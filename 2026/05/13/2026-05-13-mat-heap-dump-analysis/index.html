用 Eclipse MAT 分析 Java Heap Dump：CLI + GUI 操作手册

Posted on 2026-05-13 In Debug

来源: AI Chat | 日期: 2026-05-13

MAT 核心概念

Eclipse Memory Analyzer Tool（MAT）是分析 Java heap dump（.hprof）的标准工具。

几个必须理解的概念：

  • Retained Heap：某个对象被 GC 掉后，连带能释放的总内存。Dominator Tree 按这个排序，最大的就是你应该首先关注的
  • Dominator Tree：谁”控制”了最多内存 —— 如果 A 是 B 的唯一引用路径，A 就 dominate B
  • Hibernate L1 Cache / SessionImpl：Hibernate 的一级缓存，把所有加载过的实体以 MutableEntityEntry（含 loadedState 快照）的形式持有，直到 Session 关闭
  • OSIV（Open Session in View）：Spring 的机制，把 Hibernate Session 绑定到整个 HTTP 请求生命周期，期间所有加载进来的对象都不释放

CLI 操作步骤（无 GUI 批量分析）

输出是 ZIP 文件，解压后用浏览器打开 index.html。适合在没有图形界面的服务器上预处理大 dump，然后把报告传回本地看。

GUI 操作步骤（交互式排查）

1. 打开 Dump

File → Open Heap Dump，等待索引建立（9 GB 约需 5–10 分钟）。

2. Overview 页面

第一眼看整体占用分布，注意 “Biggest Objects” 区域——里面直接标出最大的持有者。

3. Dominator Tree

Window → Heap Dump Details → Dominator Tree

按 Retained Heap 降序排列，展开最大的对象看它在持有什么。典型的 Hibernate OOM 场景会在这里看到大量 SessionImpl。

4. OQL 查询

File → OQL，用 OQL 精确查询特定类的实例：

注意：MAT OQL 不支持 COUNT(*)，用 SELECT * 后在状态栏读实例数。

5. Path to GC Roots

右键某个对象 → Path to GC Roots → exclude weak/soft references

顺着引用链往上找，找到是哪个线程 / 哪个 HTTP 请求持有了这批对象。

6. 查看对象字段

右键 → Open in Inspector，可以看到对象所有字段的当前值——用来确认具体是哪条业务数据导致问题。

常见坑

问题 原因 解法
OQL: Encountered '*' at line 1 OQL 不支持 COUNT(*) 改用 SELECT *，看状态栏数量
Thread Overview 在 Window 菜单找不到 MAT 版本差异，部分版本没有这个 view 改用 OQL + Path to GC Roots 代替
打开 dump 极慢或 MAT 自身 OOM MAT 默认 heap 只有 1 GB 编辑 MemoryAnalyzer.ini，加大 -Xmx，如 -Xmx12g

关键收获

  • Dominator Tree 是入口，Retained Heap 最大的对象就是根因的方向
  • Hibernate L1 Cache 是隐性内存放大器：Hibernate.initialize() 会把整个懒加载集合（含二进制内容）全部拉进 Session，OSIV 再让这些对象跨越整个请求生命周期不释放
  • 功能正确 ≠ 内存安全：只需要元数据的场景调用了加载全量内容的方法，在低负载下不可见，高并发下成倍放大
  • CLI 模式（ParseHeapDump.sh）适合在没有图形界面时预生成报告，大幅减少传输体积
  • OQL 是定量分析的核心工具：先用 SELECT * 统计数量，再配合 Inspector 和 Path to GC Roots 确认业务上下文
